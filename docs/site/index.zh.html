ahsir — 基于 A2A 的多 Agent 调度器

一个小型 Go control plane：把 LLM 驱动的 agent 作为本地进程运行，让它们通过 A2A 协议互相通信，并让 Claude Code 或 Codex 通过 CLI 与内置 skill 驱动整个 fleet——local-first、 可恢复、可审计。

官方文档 · 生成于 2026-06-08

1 · 概览

ahsir 是什么

ahsir 把 Claude 和 Codex CLI 变成 A2A-compatible runtime，并在单机上调度一组这样的 runtime。每个 agent 都是一个 持久化的 persona——固定的 system prompt、一个 provider 后端、独立的文件系统权限、以及按会话持久的 记忆——通过 A2A 协议 寻址。一个中心 scheduler 负责 agent 生命周期、一个发现用的 registry、以及一个 HTTP gateway，所有调用都经它中转，从而做到可见、 可恢复、可审计。

你有两种驱动方式，底层都是同一个 CLI：

  • 直接驱动 —— ahsir list / chat / status / trace / history / doctor。
  • 通过 agentic host 驱动 —— Claude Code 或 Codex 加载内置的 orchestrator skill，由它告诉 host 何时该把任务委派给某个 specialist agent、 以及如何调用 CLI。

它不是什么

  • 不是 MCP 的替代品。 控制面是 CLI 加 skill。MCP server 模式被评估过、 但被有意推迟（见 Roadmap）。
  • 不是云端 agent platform。 差异化在于 local-first、CLI-native、 可恢复、可审计——不是一个托管的多租户服务。
  • （暂）不是多机系统。 scheduler 只绑 loopback；信任边界是单机上的 单个 OS 用户。

心智模型

把 ahsir 想成一个 面向 persona 的进程 supervisor + 消息路由器。一个 persona（agent） 在 agent-card.yaml 里配置一次；scheduler 负责把它拉起、保活、注册到 registry 供发现、 并把 A2A 消息路由给它。会话以 A2A contextId 为 key；agent 把该 context 的记忆保存在 一个长驻的 provider 子进程里，scheduler 能在崩溃后恢复它。

2 · 设计原则

下面所有功能都是这五条承诺的体现。当两个目标冲突时，按此优先级裁决。

1 · Local-first，默认零配置。 最常见的路径——单机单 OS 用户——必须无需任何配置即可工作。secret 自动生成、CLI 自动发现、 端口自动分配。只有在真实威胁成立的地方才引入摩擦。
2 · CLI-native，而非 protocol-first。 控制面是文本进、文本出的命令，agent（或人、或 shell 管道）都能驱动。结构化协议（线上的 A2A、 未来的 MCP 模式）服务于 CLI，而不是反过来。
3 · 可恢复。 agent 崩溃、claude 被 kill、scheduler 重启——任何一种都不应丢失会话。重要的状态 （context→session 映射、invocation ledger、transcript）都被持久化，让工作得以续跑而非重来。
4 · 可审计。 每一次中转的调用都被记录。ahsir trace 重建 agent 调用图；ahsir history 回放一段会话。scheduler 处在调用路径上，正是为了让一切可见。
5 · 诚实的边界。 凡是尚未成立的保证，都被明确标注为"推迟"，而不是含糊地暗示已具备。Hardening 先于扩展：系统会 明说哪些是已可依赖的 foundation、哪些只是 potential。

3 · 架构

组件

组件包职责
ahsir（scheduler + CLI）cmd/ahsir 启动 scheduler；提供用户命令（list/chat/status/trace/history/doctor/agent）。
ahsir-agentcmd/ahsir-agent 每个 persona 一个。承载 A2A 端点、加载 agent card、驱动 provider CLI。
Schedulerinternal/scheduler agent 生命周期与监督、HTTP gateway、配置、invocation ledger、admin token。
Registryinternal/registry agent 注册、心跳存活、name→card 查找。一个纯内存 store。
Wrapperinternal/wrapper A2A server/client、executor（agent 循环）、SessionPool、provider session、 transcript store、持久化。
Scheduler clientinternal/schedulerclient CLI 用来与运行中的 scheduler 通信的轻量 HTTP client。

请求流

两个入口最终汇聚到同一条 agent 侧路径。scheduler 始终留在环路中，负责发现、中转与审计。

  Claude Code / Codex ──(orchestrator skill)──┐
                                              ▼
  人 / shell ─────────────► ahsir CLI ──► scheduler gateway  :9800
                                              │   POST /agents/{name}/chat        (缓冲式)
                                              │   POST /a2a/{name}                (原生 A2A 代理)
                                              │   GET  /agents/{name}/tasks/{id}  (任务状态)
                                              │   GET  /agents/{name}/history/{ctx}
                                              │   GET  /agents, /invocations, /config/timeouts
                                              │   POST/DELETE /admin/agents       (受控)
                                              ▼
                              registry (发现)  +  invocation ledger (审计)
                                              │
                            A2A JSON-RPC message/send | message/stream
                                              ▼
                    ahsir-agent  :loopback        ahsir-agent  :loopback
                    ├ A2A server (token 校验)     ├ A2A server
                    ├ executor (agent 循环)       ├ executor
                    └ SessionPool by contextId    └ SessionPool by contextId
                              │                              │
                    claude --resume / codex exec resume <thread>

一个 turn 的流程：gateway 在 ledger 记一条 invocation → 经 A2A 转发给 agent → executor 为该 contextId 打开（或恢复）Session → provider 产出回复 → executor 记一条 transcript turn → gateway 落定 ledger 条目并返回。

进程与信任模型

  • scheduler 只绑 127.0.0.1。非 loopback 的 network.bind 会被显式拒绝。
  • agent 作为 scheduler 的子进程运行，各自占一个自动分配的 loopback 端口。
  • scheduler→agent 的 A2A 调用带一个 per-agent 的 internal token，由 wrapper 校验；scheduler 只把它发往自己在 spawn 时记录的 loopback 地址。
  • 控制面（agent 生命周期、registry 写）由 admin token 守门。信任边界是 "能读到该 token 的 0600 文件" 的那个 OS 用户。

4 · 核心概念

术语含义
Agent / persona 一个配置好的 specialist：固定 system prompt、provider、文件系统权限、skills。对应一个 ahsir-agent 进程，由 agent-card.yaml 定义。
contextId A2A 会话 key。共享同一 contextId 的消息命中同一个 provider session 并累积 记忆。省略它则是一次性的隔离 turn。
Session 一个 provider 后端的会话 runtime。ClaudeSession 是一个长驻 claude 子进程；CodexSession 每个 turn fork 一次 codex exec、按 thread id 恢复。 两者实现同一个 Session 接口。
SessionPool contextId → Session 的映射，带 idle 驱逐（保留 sessionID 供 resume）、并发上限、以及 per-context 的 FIFO turn gate。
Registry 发现：agent 注册 card 并心跳；查找解析 name→card。存活状态在读取时派生。
Gateway scheduler 唯一的 HTTP 端口。中转 chat/task/history、代理原生 A2A、暴露只读视图、并守门控制面。
Invocation ledger 每次中转调用的 append-only JSONL（started → queued → completed/failed）， 含有界的 user-text 预览。启动时回放；支撑 ahsir trace 与崩溃恢复。
Transcript per-context 的完整会话记录（speaker、完整问、完整答），由 wrapper 写入；支撑 ahsir history 与接力工作流。

5 · 功能

调度与生命周期

  • scheduler 自有的 A2A 入口。 公开的原生 A2A 流量走 POST /a2a/{agent}， 于是用户调用和 agent-to-agent 调用对 scheduler 都可见、都被记录。
  • 动态 agent 生命周期 —— 无需重启 scheduler。 ahsir agent new 生成 card、写入 ahsir.yaml、并经 POST /admin/agents 在运行中的 scheduler 上拉起它—— 新 agent 热注册，list / chat 立刻可用；ahsir agent delete 停掉它（文件保留）。 只有这几种情况才需要重启：传了 --skip-start、运行 agent new 时 scheduler 没开、或者手改了 ahsir.yaml。（改已有 card 是重启那个 agent，不是 scheduler。）
  • 监督与重启。 若 agent 进程意外退出，或其 /healthz 连续失败， scheduler 以指数退避在同一端口重启它。主动停止则是终态（不重启）。
  • 可判定的启动。 listener 同步 bind，端口冲突即作为 start 错误暴露；自动分配的 端口会探测可 bind 性并跳过外来 listener；Start 中途失败会回卷已启动的一切。
  • 进程树清理。 agent（及其 provider 子进程）跑在 process group 里，关停时 回收整棵树。

Session 与恢复

  • 多 provider session。 Anthropic（Claude）、Zhipu 与 DeepSeek （Anthropic 兼容端点）、以及 Codex。provider、base URL、API key、model 按 agent card 配置； wrapper 把它们翻译成 CLI 所需的环境变量。
  • 可恢复会话。 Claude agent 用 claude --resume=<session_id> 恢复；Codex agent 用 codex exec resume <thread_id> 恢复。
  • 持久化 session 映射。 每个 agent 写 <workspace>/.a2a/sessions.json（contextId→sessionID），受 pool.evicted_ttl / pool.max_evicted 约束，于是重启后恢复既有会话 而非从头开始。
  • per-turn 超时对齐。 两个 provider 都把 runtime.timeout 作为 真正的 per-turn deadline；超时则该 turn 干净失败、session 被驱逐且保留 sessionID 供 resume。
  • 重启续跑。 在一次受监督的重启后，scheduler 借助 ledger 为带 contextId 的被中断工作发送一条续跑 prompt。
  • pool 容量控制。 pool.max_active 限制单 agent 的并发活跃 provider 进程数；overload_policy 为 reject 或 evict-lru。
  • 会话记录的留存与删除。没有手动删除入口——记录按时间在进程启动时自动清理（compaction）：invocation ledger（驱动左栏会话列表与右栏轨迹）保留 completed 7 天、incomplete 30 天（scheduler 启动时清理）；每个 agent 的 transcript（每个 context 的消息历史）在最后一轮超过 30 天后，连同 index.json 条目一并删除（agent 启动时）；圆桌日志同样 30 天（scheduler 启动时）。另有 pool.evicted_ttl 控制 session 映射的遗忘，决定一段旧会话之后还能否 --resume。

共享 context 协作 2026-06-08

同机上多个 client 可以在同一个 contextId 内协作。

  • Speaker 归因。 ahsir chat --as <name>（默认取 OS 用户名） 为每个 turn 打标；executor 在 user text 前加 [speaker: X]，并向 system prompt 追加 一句多说话人指令，让模型把陈述归到正确的人。speaker 会出现在 ahsir trace 里。 不带归因时，prompt 与之前逐字节一致。
  • per-context FIFO 队列。 当同一 context 上已有 turn 在飞时，第二个 turn 按到达顺序排队等待，而非直接失败。受 pool.queue_depth 限制（默认 4）； 队满则退化为 busy/409 信号，而 queue_depth: 0 恢复此前的 fail-fast 契约。不同 context 仍完全并行。
  • 基于 task 的异步。 ahsir chat --async 提交 turn 后立即返回一个 task id（A2A configuration.blocking=false）；用 ahsir status 轮询。 默认模式则是提交后内部轮询——同样的同步体验，但不长占连接。
  • Transcript 回放。 ahsir history <agent> <contextId> 回放谁说了什么、agent 答了什么——这是有人中途接手会话时的接力路径。
隐私说明。 transcript 存储完整会话内容（不同于 ledger 的有界预览），因为回放正是它的目的。它以 owner-only 权限写入（0700 目录 / 0600 文件）；contextId 被 hash 进文件名，所以 caller 提供的 id 永不以原文落到文件系统。 受认可的读取路径是受 token 校验的 /history 端点。

房间：多 Agent 协同 + 圆桌 2026-06-11

一个 room 让多个 agent 在同一个共享对话里讨论 —— 它们能看到彼此的发言。room id 就是共享的 contextId，复用现有 session + speaker 机制，无需改 wrapper。room 有两种话语权模式（POST /rooms 的 mode，默认 relay）：

① 多 Agent 协同（mode: relay）：hub-and-spoke、@ 点名驱动，适合委派型协作。

  • @ 点名轮转，operator 和 agent 都能用。消息里第一个 @<参与者> 成为下一个发言者，所以一个 agent 可以把问题抛给同伴。code span 里的 @名字 是被引用的 token，不是寻址指令。
  • 组织者回交。无人被点名时，控制权交还房间的组织者 —— operator（停下等你的下一条消息）或指定的主持 agent（它接手并决定谁继续）。
  • 增量转述。轮到某 agent 时，只把它上次发言以来没看过的 transcript 喂给它（首次参与者拿到全部历史）。成本有界、无广播风暴、不丢上下文 —— 它自己的 session 保留到上次发言为止的一切，delta 补齐缺口。
  • 防跑飞。自治的 agent↔agent 链由 maxChain（两次 operator 消息之间的轮数，默认 8）兜底；每条 operator 消息重置预算。

② 圆桌（mode: roundtable）：真正的圆桌——共识轮（德州扑克式），扁平无 chair，适合模糊、要取舍的决策（如 OKR 评审）。

  • 一轮 = 随机顺序走一整圈：逐个问遍参与者（后发言者能看到本轮在先者的内容——共享广播）。每人要么发言，无异议则回 同意。约定由每轮 prompt 注入，无需改 agent 的 system prompt。
  • 滚动共识小结。一个专设 moderator agent（非参与者，跑在自己的 <roomId>#mod contextId、不污染共享 transcript、无权决定谁发言）每轮产出一份可见小结、作为下一轮锚点，分三栏：【已达成】（锁定、承接、不重议，除非有人推翻其假设）、【待议】（逐轮收窄）、【纠偏】（点名 @<agent> 指出谁跑偏命题/过度发散，让他下一轮收敛）。待议清空即共识，其【已达成】就是结论。
  • 预算（默认 12 轮）内未共识 → 交还 operator；operator 抛新问题即开新循环。建房：POST /rooms {"mode":"roundtable","participants":[...],"moderator":"<agent>","budget":12,"message":"<问题>"}。设计见 specs/2026-06-10-roundtable-mode.md。

HTTP：POST /rooms、GET /rooms、GET /rooms/{id}、POST /rooms/{id}/say、POST /rooms/{id}/stop。圆桌的每个 turn 都记入 ledger（source=roundtable），所以 trace 能看到。room 已持久化（每个 room 一份 <roomId>.jsonl），scheduler 重启时重建；恢复的 room 回到 waiting 状态（active/waiting 这种瞬时状态不持久，stopped 会持久）。超过 30 天的日志启动时清理。可运行示例：example/roundtable/。

Web 控制台 2026-06-09

一个可选的独立进程（ahsir ui），提供单页浏览器控制台并代理 gateway。它不含 LLM、不做编排 —— 是个薄代理 + 静态 SPA。

  • 1:1 对话任意 agent；回复按 Markdown 渲染（标题、粗斜体、代码块、列表、引用、链接、GFM 表格），每个气泡显示发言者和时间戳。
  • 左栏的会话列表由 invocation ledger 聚合、以 contextId 为轴；右栏是 agent 卡详情与轨迹时间线。
  • 圆桌模式驱动 /rooms API：发起房间、看合并 thread、发 operator 消息（可 @）、结束。
  • 消息操作（hover 气泡时显形）：复制复制该条原文；直接回复（仅圆桌 agent 气泡）把 @<发言者> 放到输入框开头。右栏的参与者行 / agent 卡片头部也可拖入输入框，在光标处插入 @<agent>，省去手打点名。
  • 拖或粘贴文件进输入框插入本地路径（⌘V 粘贴剪贴板图片同样支持）。浏览器隐藏拖入/粘贴文件的真实路径，所以控制台把字节上传到 POST /api/upload、copy 到本地上传目录，再把绝对路径插到光标处（claude 自己去读，如 看下 /tmp/.../shot.png 报的什么错）。任意文件类型、可多选。
  • 房间 + 提醒。支持多 Agent 协同与圆桌两种建房流（见上节）；圆桌 thread 按「第 X 轮」分隔、moderator 小结渲染成独立卡片，右栏轨迹也按轮分隔。@<参与者> 显示为蓝字、@operator（你）为深蓝 pill；有 agent @ 你时总会弹一个页内 toast，并且仅在标签页不活跃（隐藏或失焦）时额外触发声音 + 浏览器弹窗 + 标签页标题/favicon 闪烁，你切回（或本就在）这个页面时立即停止。点轨迹节点可跳到对应气泡;滚上去时有「跳到最底端」浮钮。

上传目录默认 $TMPDIR/ahsir-uploads（用 ahsir ui --upload-dir 覆盖，或设 AHSIR_UPLOAD_DIR 让控制台和 agent 一处对齐）。agent 要能读到拖入的文件，需 filesystem.enabled: true——这类 agent 启动时会自动把上传目录加进 allowed_paths（--add-dir），零配置即生效。本地优先：路径有效是因为控制台、上传目录、agent 同机。Markdown 渲染 XSS 安全（先转义、再 tokenize 成固定标签集；链接限 http(s)/mailto）。启动：ahsir ui --addr 127.0.0.1:9801 --scheduler http://127.0.0.1:9800。

MCP 隔离 2026-06-09

agent 运行 claude 时一律带 --strict-mcp-config，因此绝不继承 operator 的全局（~/.claude.json）或项目（.mcp.json）MCP server。默认 —— 没有 mcp: 段 —— 表示零 MCP server：隔离、快、省的基线（继承宿主 MCP 会撑大一次琐碎 turn 的 input token、增加每次调用的初始化开销，也是权限外泄风险）。

  • 按 agent 显式启用：卡里的 mcp.servers（claude mcpServers 形状，原样透传）或 ahsir agent new --mcp-config <file>。
  • Codex 通过自己的 CODEX_HOME config.toml 配置 MCP，所以在 codex agent 上写 mcp.servers 会报错，而非静默忽略。

模型 Provider 2026-06-10

每个 agent 在 agent-card.yaml 的 runtime 块里选自己的模型后端：claude（Anthropic 及 DeepSeek/Zhipu 等兼容端点）或 codex。高层字段 provider / baseURL / apiKey / model 被翻译成 CLI 认的环境变量（见 internal/wrapper/runtime.go）。

关键规则：wrapper 只注入你真正写了的变量。baseURL 和 apiKey 同时为空时不导出任何 ANTHROPIC_*，claude 就回退到它自己存的登录。${VAR} 严格展开（变量未设则 agent 启动即报错）；baseURL 非空但 apiKey 空会被拒绝（否则下游静默 401）。

A. Claude Code 本地登录（无 API key）。复用 claude 已登录的订阅 / OAuth（先跑 claude 再 /login）。

runtime:
  command: claude
  provider: anthropic
  baseURL: ""        # 空 → 不设 ANTHROPIC_BASE_URL
  apiKey: ""         # 空 → 无 token → claude 用自己的登录
  model: ""          # 空 → Claude Code 默认；或写 claude-opus-4-8
  timeout: 600s

前提：跑 ahsir start 的用户 / $HOME 与 ~/.claude 登录一致，且启动环境里没有 export ANTHROPIC_API_KEY / ANTHROPIC_AUTH_TOKEN / ANTHROPIC_BASE_URL（否则会盖过登录、改走 API 计费）。

  • B. Anthropic API key：provider: anthropic + apiKey: ${ANTHROPIC_API_KEY}，model 可选。
  • C. DeepSeek / Zhipu（Anthropic 兼容）：provider: deepseek（或 zhipu）+ apiKey: ${MODEL_API_KEY} + model: deepseek-v4-pro；baseURL 走 provider 自带默认，不用写。
  • D. Codex：command: codex + provider: codex，用每 agent 独立的 CODEX_HOME 和 Codex 自己的登录；此处不支持 baseURL。

ahsir agent new 脚手架默认写 Anthropic —— 方案 B（provider: anthropic、不写 baseURL → 官方 api.anthropic.com、apiKey: ${ANTHROPIC_AUTH_TOKEN}、model: claude-opus-4-8）。要用方案 A（本地登录）传 --api-key-env ""；要 C/D 传 --provider deepseek|zhipu|codex。改卡后重启该 agent（控制台「重启生效」或 POST /admin/agents/{name}/restart）才生效。

可观测性

  • ahsir trace [contextId] —— 把 invocation ledger 呈现为 agent 调用时间线：id、source（带 speaker）、agent、method、状态、耗时、预览。
  • ahsir history <agent> <contextId> —— 单段会话的 完整 transcript 回放。
  • ahsir doctor —— 健康检查清单：config 文件、PATH 上的 provider CLI、scheduler 可达性、各 agent 在线状态、以及 CLI 是否能找到 admin token。
  • 结构化日志。 scheduler 会 tee agent 的 stdout，于是 agent 间的 A2A_CALL 派发、turn 耗时、token/cost 统计都能在一处 grep 到。

鉴权 2026-06-08

控制面——agent 生命周期与 registry 写——由单个 admin token 守门； 数据面（chat、history、tasks、trace、list）在本基线中保持开放。

  • 自动生成 token。 ahsir start 首次运行时在 ahsir.yaml 旁写一个 0600 的 admin-token 文件，之后复用。AHSIR_ADMIN_TOKEN 可覆盖该文件（CI / 容器），且不落任何磁盘。
  • 同用户零摩擦。 CLI 读同一个文件，所以 agent new/delete 直接可用； 另一个 OS 用户——读不到该文件——被挡在控制面之外。
  • 覆盖保护。 未鉴权的同名注册被拒（401），堵住 registry 静默覆盖 漏洞。scheduler 拉起的 agent 通过 --admin-token 用该 token 鉴权自己的心跳。
  • internal token 泄漏修复。 scheduler 只把 per-agent 的 internal token 发往 它在 spawn 时记录的 loopback 地址——绝不发往 registry card 里的 URL（写操作本可把它改指向 攻击者）。仅凭 card 已知的 agent 不会拿到 internal token。

9 · 安全模型

本基线确立了一条真实的信任边界，并堵上了 2026-06-07 对抗式 review 里风险最高的 几个洞。它同时明确说明尚未覆盖什么。

两个 token，两种用途

Token保护对象生命周期
X-Ahsir-Admin-Token控制面：agent start/stop、registry 写。 自动生成的 0600 文件（在 ahsir.yaml 旁），或 AHSIR_ADMIN_TOKEN。 由 scheduler、CLI、被拉起的 agent 共享。
X-Ahsir-Internal-Tokenscheduler→agent 的 A2A 调用（每 agent 一个）。 每次 spawn 生成；只发往该 agent 记录在案的 loopback 地址。

信任边界

能读到 admin-token 文件的那个 OS 用户。在共享机器上，另一个用户——被 0600 挡住—— 无法 start、stop 或劫持 agent。数据面（chat/读）在此层级保持开放，因为威胁模型是多用户对控制面的 滥用，而非在 loopback 上窃听。

已就位的 hardening

  • race-free 的 registry 与 session pool；go test -race 是可信门槛。
  • provider arg sanitizer 从 runtime.args 剥离 sandbox/permission 绕过类 flag。
  • 所有 gateway body 上 MaxBytesReader；ledger 预览限 512 字节；ledger、agent-card、 transcript 文件均 0600 写入。
  • 非 loopback 的 network.bind 被拒；A2A 代理只在响应体转发完成后才落定 ledger （中断的流记为 failed）。
已推迟（明说，而非暗示）。 非 loopback / 跨机访问； 多 principal 与 RBAC；数据面鉴权；把 token rotation 做成命令（今天的做法：删文件 + 重启）。 代码结构已为"引入非 loopback bind 时再补数据面守门"留好口子。
